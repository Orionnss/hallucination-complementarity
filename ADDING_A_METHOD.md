# Protocol to Add a Method to the Evaluation Pipeline

Status: draft v0, branch `methodological-issues`. This document is a companion to
`PROTOCOL.md` and `DESIGN.md`. `PROTOCOL.md` says which comparisons are valid. This
document says how to add a method so that a valid comparison is possible.

## 1. Purpose

To compare methods fairly, we must run each method with **its own source code**. We must
not use our own interpretation of the paper. Then we must make each method:

- read the same items, generated by the same generator,
- read the same model trace, from one shared extraction pass (rule R2),
- give the same output shape,
- go through the same splits, threshold rule and metrics.

We also separate each method into two parts: the **feature extractor** and the
**reader** (the classifier). Then we can combine each extractor with each reader in a
grid. This grid is step 3 of `PROTOCOL.md`. It tests problem M1 (reader confound).

## 2. Rules

These rules apply to all methods. If a method cannot obey a rule, record a deviation
(§9). Do not change the rule.

**R1. The harness owns the evaluation. The method owns the signal.**

| The harness owns | The method owns |
|---|---|
| Datasets, item pool, `pool_seed` | How it reads the model (layers, tokens, heads) |
| The generation prompt and the generated answer | Its preprocessing of the model output |
| The labels (3-judge majority, INVALID removed) | Its feature computation |
| Seed draws, grouped folds, inner split | Its native reader and its native hyperparameters |
| The threshold rule and all metrics | Its native threshold (we record it, but do not use it for the main results) |

**R2. One shared extraction pass.** The model runs once per item, in stage 1. The harness
generates the answer with `generate()` and keeps the attentions, hidden states and logits
of that same call. This is the **trace** (§5.0). The scored answer and the features of
every method come from this one call.

- Adapters never run the model. Stage 1 calls each adapter while the trace is in memory.
  Each adapter stores only its feature blocks.
- The trace is not stored, because it is too large (the attentions alone are about 13 GB
  per item at T = 2000). Thus, to add a method later, run stage 1 again with only the new
  adapter. Stage 1 must then produce the same generated ids and the same trace
  fingerprint (§5.0). If it does not, stage 1 stops.
- Exception: methods of type D and E (§3) need more model calls, for example samples, a
  second prompt or an external model. Put these calls in one declared **secondary pass**,
  shared by all methods that need it. The scored answer stays the stage-1 answer.

**R3. Use the original code for the core.** Copy the original functions that compute the
features and the score. Do not write them again from the paper. If you must change a line,
record the change as a patch (§4.3).

**R4. The extractor never sees a label.** Only the reader sees labels. If a method uses
labels during feature computation (for example to select heads or layers), move that part
into the reader. Then the inner split can fit it.

**R5. One output contract.** Each extractor gives a feature block with a declared type
(§5.1). Each reader gives one finite float score per item. A higher score means
"hallucinated" (§5.3).

**R6. Prove that the adapter is correct before you evaluate.** Do the fidelity tests of
§7 first. A method that fails the tests does not go into the grid.

## 3. Method types

Classify the method first. The type decides which parts of this protocol apply.

| Type | Description | Examples | Reader |
|---|---|---|---|
| **A. Supervised probe** | Features from model internals, plus a trained classifier. | SAPLMA, LapEigvals, ICR | Native classifier + shared readers |
| **B. End-to-end trained** | The feature transform and the classifier train together. | CHARM | Native model. A frozen-embedding variant can go into the shared readers (§5.2). |
| **C. Training-free score** | The method gives a score directly. It has no classifier. | Token log-prob, entropy, P(True) | Identity reader (score as is) + shared readers on the score features |
| **D. Sampling-based** | The method needs k extra generations. They go into the shared secondary pass (R2). | Semantic entropy, SelfCheckGPT | Identity reader + shared readers |
| **E. External-model** | The method uses a second model (NLI, verifier, judge). It runs in the shared secondary pass (R2). | NLI consistency | Identity reader + shared readers. Record the external model as a dependency. |

A method can have more than one type. In that case, apply all the parts that are
relevant.

## 4. Steps to add a method

Do the steps in this sequence. Each step gives an output. Put all outputs in
`src/halluc/methods/<name>/` (layout in §8).

### 4.1 Step 1 — Source intake

1. Find the official code. Use the link in the paper, or the link that the authors give.
   If there is no official code, record "no official code". Then use the paper. Mark the
   method as **reimplemented**, not **adapted**.
2. Pin the exact version: repository URL, commit SHA, licence, and the version of the
   paper (for example arXiv v2).
3. Check the licence. If there is no licence, you do not have permission to copy the
   code. In that case, do not put the code in this repository. Clone it into
   `original-repos/<name>`. Git ignores this directory. The adapter loads the code from
   there (§4.3). Ask the authors for a licence before publication.
4. Write `SOURCE.md` with these items.

**Output:** `SOURCE.md`.

### 4.2 Step 2 — Read the code and write the method card

Read the code from the entry point to the score. Find these five parts:

| Part | Question to answer |
|---|---|
| **Input** | What does the code read? Text, token ids, hidden states, attentions, logits, samples? |
| **Preprocessing** | Which prompt format? Which tokens (all, answer only, last)? Which layers and heads? Which normalisation? |
| **Feature computation** | Which equation? Which function and lines implement it? |
| **Reader** | Which classifier? Which hyperparameters? Which values are searched, and which are fixed? |
| **Decision** | Which threshold? Fitted on which data? |

For each part, write a line reference to the code and a reference to the equation in the
paper. Compare the code with the paper. If they are different, record both versions. Use
the **code** as the default, because the code produced the published numbers. Make the
paper version an option.

Also list the parts of the source code that **we do not use**, and say why. Usually these
parts are:
- their data loaders (the harness gives the items),
- their generation loop (R2),
- their labelling (the harness gives the labels),
- their splits and their metrics (the harness owns them).

**Output:** `METHOD_CARD.md`. §10 gives the template.

### 4.3 Step 3 — Isolate the core

1. Clone the repository into `original-repos/<name>` at the pinned commit. Do not change
   the files.
2. List the files that contain the code that the adapter runs. Record the sha256 of each
   file in an `UpstreamSpec` (`src/halluc/methods/upstream.py`). The loader checks the
   commit and the hashes before each import. It does not execute the package `__init__`
   files, because they usually import the whole application. Replace the modules that
   are imported only for code paths that you do not call with stubs. The stubs raise an
   error if the code calls them.
3. If a change is necessary, apply it at load time, in the namespace of the upstream
   module. Do not change the file on disk. Give each patch one id and one reason, and
   record it in the method card. Examples of valid reasons:
   - device placement,
   - batch size,
   - removal of a hardcoded path,
   - a dependency version.

   A change to the computation is **not** a valid patch. If a change to the computation is
   necessary, record it as a deviation (§9).
4. Do not install the upstream package. Its pinned dependencies usually conflict with the
   torch and CUDA stack of this project. Import only the modules that you need. Do not
   change the project stack. The `env.sh` of the cluster records the stack.

**Output:** `upstream_spec.py` (the `UpstreamSpec`, the loader and the patches).

### 4.4 Step 4 — Write the extractor adapter

The adapter connects the shared trace to the original core. Stage 1 calls it once per
item, inside its loop (R2). It does three things:

1. **Take the input from the trace.** Use the **native view** of the trace (§5.0) when
   the original code reads the output of `generate()`. This is the usual case: the
   official LapEigvals, ICR and CHARM code all read it. Then give the trace to the
   original code without conversion. Use the **stacked view** only when the original code
   reads full matrices.
2. **Call the original core.** Call the upstream function. Do not copy its logic into the
   adapter.
3. **Convert the output.** Change the output of the core into a typed feature block
   (§5.1).

The adapter declares what it needs from the trace: `attentions`, `hidden_states`,
`logits`. Stage 1 asks `generate()` for the union of these needs. The adapter must not
run the model, and must not keep a reference to the trace after it returns.

A method that needs more model calls (types D and E) does not get its own stage. It
declares its calls in the shared secondary pass (R2), which uses the same item ids and
checkpoints as stage 1.

**Output:** `adapter.py` with an adapter registered for stage 1.

### 4.5 Step 5 — Write the native reader adapter

1. Wrap the native classifier of the method as a reader (§5.2).
2. Use the native hyperparameters and the native search space. If the paper searches a
   space, search the same space on the inner split. If the paper fixes a value, fix it.
   Record in the method card which values are searched and which are fixed.
3. If the native reader uses data that the harness does not give, for example a separate
   validation set for early stopping, use the inner split. Record that it uses the inner
   split.

**Output:** a reader registered in `READERS`.

### 4.6 Step 6 — Fidelity tests

Do all tests in §7. Do not go to step 7 until all tests pass, or until each failure has a
recorded deviation.

**Output:** `tests/test_<name>_fidelity.py` and a fidelity report in the method card.

### 4.7 Step 7 — Register the method in the grid

1. Declare the feature type of each block that the extractor gives.
2. The harness then combines the extractor with each compatible reader (§6).
3. Record the budget of each cell: the number of configurations and the axes searched
   (problem M2 in `PROTOCOL.md`).

**Output:** a grid entry. No code change is necessary in stage 3.

### 4.8 Step 8 — Run and validate

1. Run stage 1 with only this adapter (`--adapters <name> --limit N`) on one dataset. Check
   the shapes, the dtypes, NaN and inf, and the timing. Check that the generated ids are
   the same as the ids that stage 1 stored, and that the trace fingerprint is the same.
2. Make sure that the native cell gives the published *direction* of the results (§7,
   test F4).
3. Run the full grid: all generators, all datasets, all seeds.
4. The grid output (`runs/<run>/grid/`) is the only store of out-of-fold scores. Do not
   keep a special case for the method.

**Output:** `predictions.npz` and `metrics.json` for each cell, in the standard layout.

## 5. Interfaces

### 5.0 The shared trace

Stage 1 makes the trace with one call per item, at batch size 1:

```python
model.set_attn_implementation("eager")          # attention weights must exist
out = model.generate(
    input_ids, do_sample=False, max_new_tokens=256,
    output_attentions=True, output_hidden_states=True, output_logits=True,
    return_dict_in_generate=True,
)                                               # bf16, greedy
```

Stage 1 asks only for the outputs that the enabled adapters need. The generated answer is
the scored answer. There is no second forward pass.

| Field | Content |
|---|---|
| `sequences` | Prompt ids and generated ids. |
| `prompt_len` | Number of prompt tokens. |
| `n_kept` | Number of answer tokens that stage 1 keeps, after it removes the terminator (EOS, end-of-turn) and, for base models, the text after a stop string. |
| `finish_reason` | `stop` or `length`. |
| `steps.attentions` | Per step, per layer: `[1, H, q, k]`. Step 0 holds the prompt rows (q = prompt length). Each later step holds one row. |
| `steps.hidden_states` | Per step, per layer (L + 1 entries): `[1, q, d]`. |
| `steps.logits` | Per step: `[1, V]`, before any logits processor. |

The harness gives two views of the trace:

- **Native view:** the per-step tuples, exactly as `generate()` returns them, cut to the
  kept answer. Give this view to upstream code that reads `generate()` output.
- **Stacked view:** full matrices `[H, T′, T′]` per layer and `[T′, d]` per layer, where
  T′ is the number of tokens that the model read (the last generated token is never read
  back). The harness builds this view once, with zero padding of the per-step rows. Our
  reimplemented extractors (SAPLMA, our ICR, our LapEigvals) use it.

**Cut to the kept answer.** If stage 1 removes answer tokens (a stop string in a base
model, for example), it cuts both views to the kept tokens. No adapter sees tokens that
are not part of the scored answer. The method card records how the method treats the
terminator.

**Trace fingerprint.** Stage 1 records a `trace_spec`: generator id, dtype, attention
implementation, decoding settings, `max_new_tokens`, prompt-template hash, torch,
transformers and CUDA versions, and GPU name. The stage-1 manifest stores it, and the
`spec.json` of each method store copies it. A store with a different fingerprint is
refused. A later run of stage 1 (for a new method) must give the same fingerprint and the
same generated ids for every item. Otherwise it stops, because the new method would read
a different trace from the others.

### 5.1 Feature types

Each feature block declares one type. Readers declare the types that they accept.

| Type | Shape per item | Example | Notes |
|---|---|---|---|
| `vector` | `[d]` | `icr`, `lapeigvals_official` (via its k view) | Fixed d for one generator. |
| `layered` | `[L+1, d]` | `saplma` | The layer is a hyperparameter of the **reader**, selected on the inner split. Store all layers. |
| `scalar` | `[1]` or `[m]` small | log-prob, entropy | A score from a type C, D or E method. |
| `sequence` | `[T, d]`, T changes | per-token states | Variable length. Store as ragged. |
| `graph` | nodes + edges, size changes | CHARM | Use a sparse format (for example CSR). |

Rules:
- A block is a pure function of (generator, item, extractor configuration). Hash the
  extractor configuration into a `spec.json`, as the LapEigvals adapter does. If the spec is different,
  the store refuses the block.
- Use float16 only when the values fit (see `Saplma.FP16_SAFE_MAX`). If not, use float32.
- A conversion from `sequence` or `graph` to `vector` (for example mean pooling) is a
  separate, named **pooling adapter**. It is not part of the reader. Thus the grid can show
  its effect.

### 5.2 Reader interface

A reader is a `Reader` in `src/halluc/grid.py`:

```python
Reader(
    name="lapeigvals_official",
    grid=[{}],                         # search space; selected on the inner split
    build=lambda params, seed: ...,    # returns an estimator with fit(X, y), predict_proba(X)
    accepts=MATRIX_TYPES,              # feature types, see §5.1
    native_decision=native_argmax,     # the method's own decision rule, or None
)
```

- `predict_proba(X)[:, 1]` is the score: shape (n,), float, finite, higher means
  hallucinated.
- If the upstream code fits and scores in one call, wrap it in an estimator. `fit` stores
  the training rows. `predict_proba` calls the upstream function. If the upstream
  function also needs test labels (for example to compute its own metrics), give it
  placeholder labels. Then prove that the scores do not depend on them (test F6).
- A reader that needs a validation set (for example for early stopping) must take it from
  its training rows. The harness never gives test data to `fit`.
- A **block** declares its *views*: the label-free choices that make a matrix from the
  stored array, for example top-k or the layer. The harness combines the views and the
  reader grid, and selects on the inner split.
- The harness, not the reader, selects the threshold.
- The shared reader set is: identity (`scalar` only), standardise + logreg, PCA-k + logreg,
  PLS-k + logreg, MLP (published SAPLMA shape), and the native reader of each method.
  Each native reader becomes available to all compatible extractors.
- For type B methods, the end-to-end model is the native reader. To put its
  representation into the shared readers, export its frozen pooled embedding as a `vector`
  block. Fit it inside the training fold. Record this variant as a separate extractor, with
  a different name.

### 5.3 Output contract

Each (extractor, reader) cell gives, for each seed:

| Key in `predictions.npz` | Shape | Content |
|---|---|---|
| `scores__<extractor>__<reader>` | `(n,)` float | Out-of-fold score. Higher = hallucinated. |
| `preds__<extractor>__<reader>` | `(n,)` int | Decision at the harness threshold. |
| `native_preds__<extractor>__<reader>` | `(n,)` int | Decision at the native threshold, if the method has one. |
| `y`, `dataset`, `groups`, `item_ids` | `(n,)` | The same arrays as stage 3. |

Checks that the harness does on each cell:
- The score is finite for all items.
- The item ids are the same as the item ids of the stage-3 draw, in the same sequence.
- **Orientation.** If the original method gives a "truthfulness" score, the adapter
  changes its sign. Then test F5 makes sure that the AUROC is more than 0.5 on the inner
  split.

### 5.4 Metrics

The harness computes these metrics for each cell. Compute them per dataset and pooled,
for each seed. Report the mean ± sd over seeds.

| Metric | Needs a threshold | Why |
|---|---|---|
| AUROC | No | Ranking quality. Comparable with most papers. |
| AUPRC | No | Ranking quality when the base rate is low (CoQA ≈ 0.15). |
| MCC | Yes (inner split) | The main thresholded metric. Robust to the base rate. |
| Balanced accuracy | Yes | Accuracy that the base rate does not bias. |
| F1 (hallucinated class) | Yes | Many papers report it. |
| Accuracy + majority floor | Yes | Report only with its floor. |
| TPR at FPR 5% and 10% | No | Operating points for deployment. |
| Brier score, ECE | No | Only if the reader gives probabilities. Report as calibration, not as accuracy. |

`src/halluc/eval/metrics.py` has AUROC, MCC, accuracy and F1. Add the other metrics there,
so that all methods use one implementation.

## 6. The grid

```
                 reader →  identity  logreg  pca128+lr  pls8+lr  mlp_saplma  native_X  native_Y ...
extractor ↓
saplma (layered)              —        ✓        ✓         ✓          ✓          ✓?        ✓?
lapeigvals (vector)           —        ✓        ✓         ✓          ✓          ✓?        ✓?
charm (graph)                 —        —        —         —          —          ✓          —
charm_emb (vector)            —        ✓        ✓         ✓          ✓          ✓?        ✓?
entropy (scalar)              ✓        ✓        —         —          ✓          ✓?        ✓?
```

- ✓ means that the types are compatible. ✓? means that the types are compatible only if
  the native reader accepts the type.
- Each cell uses the same seeds, folds, inner split and threshold rule. Use `run_fold` in
  stage 3 as it is.
- Each cell records its budget: the number of configurations, the axes searched, the
  training rows and the number of fits.
- The **native cell** (native extractor + native reader) reproduces the published method.
  The other cells test the reader confound.
- Select the best reader of an extractor **on the inner split**. Do not select it on the
  test results. If you report "best of grid" from test results, label it as an oracle
  result.

`src/halluc/grid.py` implements the grid. It has two registries: `BLOCKS` (where a block
is on disk, its type and its views) and `READERS`. A `CellDetector` joins one block and
one reader into the `Detector` interface, so each cell runs through `run_fold` of stage 3
without changes. The existing detectors in `src/halluc/detectors.py` do not change, so
test F7 passes by construction. `scripts/run_grid.py` runs the cells and writes the output
of §5.3 with the metrics of §5.4.

## 7. Fidelity tests

| Test | What it checks | Pass criterion |
|---|---|---|
| **F1. Equivalence with the original code** | On a fixed set of inputs, run the upstream pipeline without changes, and run the adapter on the same input. Do it on synthetic per-step outputs (CPU), and on real `generate()` outputs of about 20 items (GPU, `f1_real.py`). | Bitwise equal. Both read the same trace, so any difference is an adapter error. A tolerance needs a recorded reason. |
| **F2. Contract** | Shape, dtype, finite values, declared feature type, item id sequence. | No violation. |
| **F3. Determinism** | Run stage 1 twice on the same 20 items, on the same GPU type. | The same generated ids, the same trace fingerprint, and identical blocks. A tolerance needs a recorded reason (for example, GPU scatter operations that add in a different sequence). |
| **F4. Reproduction** | Run the native cell on the setup of the paper (the same model and dataset), if this is possible. | The result is in the published direction, and near the published number. Record the difference. If the setup cannot be reproduced, record why. |
| **F5. Orientation** | AUROC on the inner split. | More than 0.5. If it is less than 0.5, the sign is wrong. |
| **F6. Label isolation** | The extractor runs on data where the labels are permuted. | The features are identical. |
| **F7. No regression** | After a change to the harness, run the existing methods again on one seed. | The reference values of the last full run do not change. |
| **F8. Synthetic run** | Run on synthetic data. | The CV machinery runs, the folds keep their groups, and no test data leaks. Do not use this run to compare methods. |

## 8. File layout

```
src/halluc/methods/<name>/
  SOURCE.md                 repository URL, commit SHA, licence, paper version
  METHOD_CARD.md            the template in §10, filled in
  upstream_spec.py          pinned commit, file hashes, loader, load-time patches
  adapter.py                stage-1 adapter: needs, extract(trace) (+ pooling adapter, if necessary)
  reader.py                 native reader adapter
  tests/
    test_fidelity.py        tests F1–F6, CPU
    f1_real.py              F1 on real generate() outputs (GPU)

original-repos/<name>/      the upstream checkout, at the pinned commit, ignored by git
```

## 9. Deviations

A deviation is any place where the adapted method differs from the original method. Each
deviation has one entry in the method card:

| Field | Content |
|---|---|
| What | The difference. |
| Why | The cause, for example memory, a different generator or a missing detail in the paper. |
| Direction | Does it help the method, make it worse, or is the effect unknown? |
| Test | An experiment that measures the effect, or "not tested". |

Examples from this repo:
- Our former CHARM reimplementation (removed 2026-10-06) used the inner split for early
  stopping, so it saw less data. Direction: worse for CHARM.
- The same reimplementation used a pinned grid, not the full published grid. Direction:
  unknown.
- The ICR pooling operator is not clear in the paper, so we search it. Direction: neutral.

Report the deviations of each method next to its results. A reviewer must be able to see
them.

## 11. Checklist before a method goes into the results

- [ ] `SOURCE.md` has a commit SHA and a licence.
- [ ] The method card is complete. Each part has a code reference and a paper reference.
- [ ] The upstream files are unchanged (the hashes verify). Each patch has an id and a reason.
- [ ] The adapter runs inside stage 1, reads only the trace, and does not call the model (R2).
- [ ] The `spec.json` of its store carries the trace fingerprint of the run (§5.0).
- [ ] The extractor does not use labels (F6).
- [ ] F1–F6 pass, or each failure has a deviation entry.
- [ ] The native cell is in the published direction (F4), or the reason is recorded.
- [ ] The existing results do not change (F7).
- [ ] The grid has a budget record for each cell.
- [ ] The out-of-fold scores are in the grid output (`runs/<run>/grid/`).
- [ ] The deviations are in the results table, next to the method.

## 12. The existing methods under this protocol

The existing methods were added before this protocol. Most of them are reimplementations,
not adaptations of the original code. To make the comparison fair, they must go through
the same steps.

| Method | Status now | Work to do |
|---|---|---|
| SAPLMA | Reimplemented. The reader is extracted and the MLP copies the published shape. | Steps 1–2 against the official code. F1 against the official code. |
| LapEigvals | **Adapted** (`src/halluc/methods/lapeigvals`). Runs in stage 1 on the native view of the shared trace (extractor `lapeigvals_official`). The 2026-10-05 validation on `main` used the earlier re-forward input. | Validate again after the full rerun. |
| ICR | **Adapted** (`src/halluc/methods/icr_probe`, extractor `icr_official`). CPU fidelity 8/8. The official pooling is the mean over response tokens (notebook). Our reimplementation `icr` is still extracted, for comparison. | F1-real, F4, F5 after the full rerun. |
| CHARM | **Adapted** (`src/halluc/methods/charm`, extractor `charm_official`, ragged graph block). CPU fidelity 6/6. Our reimplementation was removed (backup in `$HALLUC_BASE/backups/`). | F1-real, F4, F5 after the full rerun. Add the `charm_emb` frozen-embedding extractor. |
| attn_baseline, svd_baseline, log-prob | **Removed** (2026-10-06). Our own baselines, with no source to adapt. The official AttnEigvals block replaces `attn_baseline`. | None. |

The grid (§6) and the shared trace (§5.0) exist. Run the full experiment again: all
generators, from generation. Results from earlier runs are not comparable with results
from the shared trace, because the answers, the labels and the attention input change.
